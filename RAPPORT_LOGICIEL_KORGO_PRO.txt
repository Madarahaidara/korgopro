3. ARCHITECTURE ET ARBORESCENCE
================================================================================

Le projet suit une separation en couches proche du MVC :

  main.py                 Point d'entree de l'application
  core/                   Couche metier + persistance
    database.py           Engine SQLAlchemy, SessionLocal, Base, get_db()
    database_manager.py   Outillage d'administration de la base (10 Ko)
    log_manager.py        Journalisation des activites (5 Ko)
    sale_log_manager.py   Journal des operations de vente (5 Ko)
    proforma_invoice_manager.py  Logique metier des proformas (18 Ko)
    security.py           Hachage/verification des mots de passe
    bruteforce_protection.py     Anti-force brute (singleton)
    startup_manager.py    Orchestration du demarrage + splash
    models/               Modeles ORM
      user.py, customer.py, activity_log.py, sale_log.py,
      sale_models.py (9 Ko), stock_models.py (8 Ko)
  controllers/
    auth_controller.py    Authentification et recuperation d'utilisateur
  ui/
    views/                14 vues Qt (voir section 7)
    themes/               8 feuilles de style QSS + theme_manager.py
    icons/                icon_manager.py + 30 icones (SVG/PNG/ICO)
  utils/
    print_service.py      Generation/rendu des documents (68 Ko)
    print_dialogs.py      Boites de dialogue d'impression (45 Ko)
    settings_manager.py   Parametres entreprise (singleton, JSON)
    resource_path.py      Resolution des chemins (compatible PyInstaller)
    project_paths.py, helpers.py, icon_manager.py
  alembic/                env.py + revisions de migration

  LoginView -> AuthController -> DB
  LoginView --(signal login_successful)--> MainWindow
  MainWindow -> QStackedWidget de vues, permissions par role
  Vues -> Managers (core) -> SQLAlchemy -> SQLite

4. POINT D'ENTREE ET CYCLE DE DEMARRAGE
================================================================================

main.py (59 lignes) execute, dans l'ordre :
  1. Base.metadata.create_all(bind=engine)  -> cree les tables manquantes
  2. Activation du High DPI (PassThrough) pour ecrans 4K/Retina
  3. Creation de QApplication
  4. Affichage d'un splash screen moderne (ModernSplashScreen) avec
     progression 30 % / 60 % / 90 % / 100 %
  5. Chargement du theme "light" via ui/themes/theme_manager.load_theme
  6. Application de l'icone de l'application
  7. Creation de LoginView ; un signal login_successful ouvre MainWindow
  8. Fondu de sortie du splash, puis app.exec()

Point notable : le code est ecrit au niveau module (pas de fonction main() ni
de garde `if __name__ == "__main__":`). Le module ne peut donc pas etre
importe sans lancer l'application entiere.

Un StartupManager + StartupWorker (QThread) existent dans core/, avec des
etapes de progression, mais ne sont pas utilises par main.py : le chemin de
demarrage reel est synchrone. Ce module est donc du code mort en l'etat.

Modele utilisateur — core/models/user.py

          role (defaut "CAISSIER"), active, created_at, last_login,

  suppliers            : code, nom, contact_person, email, phone, address,
                         city, country, website, notes, payment_terms, active
  inventory_movements  : mouvements de stock
  expense_categories   : categories de depenses
  expenses             : category_id, amount, description, payment_method
                         (CASH/BANK/MOBILE_MONEY), reference, supplier_id,
                         user_id, date
  purchase_orders      : order_number, supplier_id, statut
                         (PENDING/ORDERED/RECEIVED/CANCELLED), total_amount,
                         expected_delivery, received_date
  purchase_order_items : order_id, product_id, quantity, unit_price,
                         total_price, received_quantity
  stock_alerts         : product_id, alert_type (LOW_STOCK/OUT_OF_STOCK/
                         EXPIRING), threshold, message, is_read

Modele ventes — core/models/sale_models.py
  sales                : sale_number, customer_id, cashier_id, sale_date,
                         subtotal, discount_amount, tax_amount, total_amount,
                         amount_paid, change_amount, payment_method,
                         payment_status, sale_status, currency (FCFA),
                         type_document (FACTURE/AVOIR), origine_proforma_id,
                         date_conversion, utilisateur_conversion,
                         statut (BROUILLON, EMISE, PARTIELLEMENT_PAYEE,
                         PAYEE, EN_RETARD, ANNULEE), date_expiration, version
                         Propriete calculee : profit
  sale_items           : lignes de vente (quantite, prix unitaire, remises)
  sale_returns / sale_return_items : retours de vente (motif, remboursement)
  proforma_invoices    : proforma_number, customer_id, created_by,
                         created_date, valid_until, montants, remises, taxes,
                         status (BROUILLON, EN_ATTENTE, ENVOYEE, ACCEPTEE,
                         REFUSEE, EXPIREE, CONVERTIE), terms_and_conditions,
                         currency, converted_to_sale_id
  proforma_invoice_items : lignes de proforma (product_id nullable = libre)

Autres : customers, activity_logs, sale_logs.

Traçabilite : le couple Sale.origine_proforma_id /
ProformaInvoice.converted_to_sale_id assure le lien bidirectionnel entre le
devis et la facture definitive — bonne pratique metier.

Devise par defaut : FCFA (marche ouest-africain), TVA par defaut : 20 %.

6. MODULES METIER (CORE)
================================================================================

core/database.py
  Engine SQLite avec check_same_thread=False (necessaire pour Qt multi-thread,
  mais expose a des acces concurrents si des threads ecrivent en parallele).
  Fournit SessionLocal, Base, init_database() et un generateur get_db().

core/database_manager.py
  Outil d'administration de la base : inspection des tables, colonnes, cles
  etrangeres, index, comptage de lignes, et execution de requetes SQL en
  LECTURE SEULE. Securise par liste blanche regex :
      ^\s*(SELECT|WITH|EXPLAIN QUERY PLAN|PRAGMA)\s
  plus une liste noire complementaire (INTO OUTFILE, INTO DUMPFILE, LOAD_FILE,
  INFORMATION_SCHEMA, PRAGMA WRITEABLE_SCHEMA, ATTACH DATABASE).
  Le comptage de lignes passe par un mapping table -> modele ORM plutot que
  par des f-strings SQL.

core/proforma_invoice_manager.py (le plus gros manager, 18 Ko)
  Cycle de vie complet des proformas : creation, numerotation, calcul des
  totaux/remises/taxes, changement de statut, conversion en vente.

core/log_manager.py / core/sale_log_manager.py
  Journalisation des actions applicatives et des operations de vente
  (audit trail).

core/security.py
  hash_password()    : bcrypt avec sel genere (bcrypt.gensalt())
  verify_password()  : verifie bcrypt ; repli SHA256 pour anciens comptes
  migrate_old_hash() : re-hache en bcrypt apres verification reussie

core/bruteforce_protection.py
  Singleton thread-safe (double-checked locking). 5 tentatives echouees
  maximum, verrouillage de 15 minutes par nom d'utilisateur.
  Limite : etat purement en memoire — un redemarrage reinitialise tout.

controllers/auth_controller.py
  authenticate()    : verifie l'utilisateur actif, valide le mot de passe,
                       met a jour last_login, migre automatiquement le hash
                       SHA256 vers bcrypt, retourne un dict utilisateur
  verify_password()  : re-verification (utilisee pour les actions sensibles)
  get_user_by_id()   : lecture d'un utilisateur

  [OK] Mots de passe haches avec bcrypt + sel aleatoire
  [OK] Migration transparente SHA256 -> bcrypt a la connexion reussie

  [OK] Suppression des f-strings SQL dans get_table_data() / comptage

  [OK] Permissions par role appliquees dans MainWindow
  [OK] Champs de tracabilite : last_ip, last_login, must_change_password
  [OK] Compte desactive (active=False) refuse a l'authentification

Faiblesses residuelles :

  [!] Le repli SHA256 dans verify_password() reste actif indefiniment : tant
      qu'un compte ancien ne se connecte pas, son hash faible subsiste.
  [!] L'etat anti-force brute est en memoire : redemarrer l'application
      annule les verrouillages (contournement trivial en local).
  [!] La base SQLite et company_settings.json ne sont pas chiffres et sont
      lisibles par tout utilisateur ayant acces au dossier.
  [!] La base korgo_pro.db et users_export.json sont presents dans le dossier
      de travail ; users_export.json peut contenir des donnees sensibles.
  [!] Les erreurs sont remontees par print() plutot que par le module logging,
      ce qui les rend invisibles dans une build sans console (console=False).
  [!] Blocs `except (ValueError, Exception)` et `except:` nus : masquent des
      erreurs reelles.
  [!] SECURITY.md est le modele GitHub par defaut, non personnalise
      (versions 5.1.x / 4.0.x sans rapport avec la version 0.1.0 du projet).
  [!] must_change_password vaut True par defaut mais aucun controle
      d'application n'a ete trouve dans le flux d'authentification.
  Alembic -> schema de la base

Points d'attention :

    risque de branche/duplication dans l'historique Alembic.
  - Une revision utilise un nom de fichier manuel au lieu d'un hash genere,

  - main.py appelle Base.metadata.create_all() : sur une base neuve les

    forcement estampillee (risque de conflit au prochain `alembic upgrade`).
  - Des scripts de migration ad hoc coexistent avec Alembic :
    init_db.py, migrate_sale_logs.py, recreate_db.py, reset_db.py.

11. BUILD, PACKAGING ET CI/CD

ignores de .gitignore). version_info.txt est present pour les metadonnees

  Declencheurs  : push sur main, tags "v*", declenchement manuel
  Runner        : windows-latest, Python 3.11 avec cache pip
  Etapes        :
    1. Checkout
    2. Installation de PyInstaller + PySide6, SQLAlchemy, alembic, pandas,
       openpyxl, bcrypt, reportlab
    3. Regeneration du fichier spec dans le workflow (gitignore) -> build
       reproductible dans la CI
    4. pyinstaller korgo_pro.spec (mode fenetre console=False, UPX active,
       icone ui/icons/logo.ico, exclusion tkinter/PyQt5/PyQt6/pytest,
       hiddenimports incluant les sous-modules des paquets et de l'app)
    5. Verification de dist\KorgoPro\KorgoPro.exe (echec sinon)
    6. Sur tag v* : Compress-Archive + GitHub Release (notes auto)
    7. Sinon : artefact de build "KorgoPro-build"

Appreciation : pipeline correct et fonctionnel. Il manque une etape de tests
et le pin des versions des dependances.

16. PROBLEMES IDENTIFIES ET RISQUES
================================================================================

CRITIQUE
  C1. Depot historiquement pollue par des artefacts de build (korgo-beta2/,
      base tzdata complete) avec des centaines de suppressions non commitees.
  C2. Aucun test automatise fiable ni execute en CI. Sur 22 866 lignes, une
      regression peut passer inapercue jusqu'a la production.
  C3. Absence de README.md : aucune instruction d'installation, de lancement,
      de creation du premier administrateur ni de sauvegarde.

MAJEUR
  M1. Fichiers monolithiques : stock_view.py (~228 Ko), admin_view.py
      (~94 Ko), proforma_invoice_view.py (~80 Ko). Maintenance difficile.
  M2. Dependances non versionnees -> builds non reproductibles, risque de
      casse silencieuse a la prochaine version majeure des librairies.
  M3. Cohabitation Alembic / create_all() / scripts ad hoc : le schema reel
      peut diverger des migrations. Deux revisions "currency" en doublon.
  M4. Aucune strategie de sauvegarde de korgo_pro.db visible. Un fichier
      SQLite unique, non chiffre, sans sauvegarde automatique = risque de
      perte totale des donnees comptables du client.
  M5. Anti-force brute purement en memoire (contournable par redemarrage).
  M6. Fichiers de donnees sensibles a la racine du depot de travail :
      korgo_pro.db, korgo_prol.db, users_export.json, activity_log.txt.

MINEUR
  m1. print() partout au lieu de logging ; en build sans console toutes les
      erreurs sont perdues.
  m2. Blocs except trop larges (`except:`, `except (ValueError, Exception)`).
  m3. Code mort ou inutilise : startup_manager.py non utilise par main.py,
      splash_screen_enhanced.py non reference, diagnonstique.py (faute de
      frappe dans le nom) laisse a la racine.
  m4. main.py sans fonction main() ni garde __main__.
  m5. Doublon self.setStyleSheet("") consecutif dans apply_light_theme().
  m6. Fichier ".txt" vide/anonyme a la racine ; rapports .xlsx generes
      commites ; facture_test.html a la racine.
